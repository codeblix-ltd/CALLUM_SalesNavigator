# Pay and tracking validation

Environment: Node fixtures and Cockroach V2 test operator. Baseline SHA: `68f5971a5e4b91d0814cd0f2b32dd18dbd64237b`.

`pnpm test` proves attempts and uncertain intents do not satisfy the payable predicate. The Cockroach integration test created an explicitly test-only, zero-amount enabled rule, confirmed a synthetic action, delivered its ACK twice, and observed exactly one ledger item referencing a source event and rule version. It also observed Pending after an explicitly `not_submitted` command: that intent became `cancelled`, generated no reconciliation command, and generated no pay. The rule was disabled in test cleanup.

This proves derivation and uniqueness for the tested connection outcome. It does not establish real scout compensation policy, actual payable rates, comment/observation eligibility, payroll approval or live-action attribution. Those require owner-approved versioned rules and further tests.

The later Cockroach regression enabled the fixture rule before reconciliation. A Pending observation after a lost action ACK produced one ledger row tied to a `connection_confirmed` source event and the tested rule version. Direct confirmation, late ACK, and `not_submitted` cases remained distinct.

The withdrawal Cockroach test produced zero pay rows across confirmed, uncertain, late-ACK, and `not_submitted` outcomes. Withdrawal compensation is not configured or implied by this implementation.

The admin API now creates a versioned pay rule and an audit event in one V2 transaction. It rejects unsafe integer values, missing enabled state, unsupported event types, invalid currency codes and duplicate versions. An admin can enable or disable an existing rule through the API and web form without editing the database; a no-op repeat does not add an event. The admin overview shows current rule versions and enabled state plus selected audit version/state fields. A focused Cockroach-backed local HTTP test passed 1/1: an unauthorized request was rejected, a **zero-amount** disabled fixture rule was created, enabled, repeated, and disabled, with three sanitized audit events, no pay-ledger row, and no admin token in stored or visible data. The test left the fixture rule disabled. This validates administration and rollback mechanics only; it does not approve a compensation rate or establish payroll policy. The shared admin token still cannot attribute the change to an individual approver.

Pending an owner-approved compensation policy and attributable approval flow, the admin API rejects both creation of an enabled positive-amount rule and activation of a positive-amount draft with `PAY_POLICY_NOT_APPROVED`. Disabled positive drafts may be recorded for review. A zero-amount fixture can still be enabled for isolation tests. The extended Cockroach-backed HTTP test passed 1/1 and verified both positive-rate denials, no inserted enabled rule, and no activation of a disabled positive test fixture. The test removed that positive fixture in cleanup. A V2 database inventory on 2026-09-26 found zero positive rules and zero positive ledger entries. The API guard does not replace database access controls or establish the policy needed to lift it. Disabling a rule affects future derivation only; existing ledger rows remain for review and are not silently rewritten.

The admin API now supports `GET /api/admin/pay/:id` for any known ledger UUID, and the web ledger shows line IDs plus a trace lookup. The response selects only identifiers, timestamps, amount/currency/status, intent state, source confirmation, canonical authorization, and rule metadata; it omits raw event details, comment text, page content, URLs and tokens. `trace_status=linked` means those stored records agree on the action, operator, run, lead, intent, event type, amount and currency. It does **not** prove a real LinkedIn outcome, rate approval, or payroll eligibility. Missing or conflicting evidence receives a distinct status. The endpoint uses the existing unique event-key index and introduces no schema change.

Focused Cockroach cases passed 1/1 each for reconciled Connect pay, reviewed-comment pay, and the admin route's authorization/invalid/missing-line responses. The Connect case also fetched its line over the authenticated local HTTP API and found no token in the response. A read-only 2026-09-26 inventory found 107 of 108 existing V2 pay lines fully linked by the same stored-field checks; the exception is one historical zero-amount `v2test_*` line with a confirmation event but no canonical authorization event. The lookup reports `missing_authorization` for that line. No historical ledger row was rewritten. This anomaly prevents claiming that every existing test line has complete authorization evidence.

The first expanded Connect integration run failed during test cleanup because it waited twice for the child server's signal exit. No pay assertion failed. The cleanup check was corrected, and the same final-code case passed on rerun.
