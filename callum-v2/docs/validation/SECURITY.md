## Follow-up review: migration and version boundary

Migration `005_global_action_targets` added a V2-only primary key on `(action_type,target_key)` and backfilled historical target keys. The control plane now claims that guard in the same transaction as a new Connect, comment or withdrawal intent. A concurrent Cockroach test used two operators and different lead IDs for one profile and observed one reservation, intent and action command. Direct writes to `action_intents` bypass the service guard, so production action creation must remain behind the control plane; V1/V2 ownership is still not atomic.

Installation issue and remote-config minimum versions now require exact, bounded V2 version strings. The focused test rejects suffixes, leading zeros, oversized components and the wrong major version, and accepts `2.5.0`. This closes a compatibility-input gap; it does not attest that an operator's reported extension build actually matches the installed package.

A local scan of all 12 `dist` files found no exact occurrence of the configured Cockroach URL. The local environment did not contain `V2_ADMIN_TOKEN`, so its value could not be compared with the package. Neither secret variable name appears in the web/extension source or distribution. The server returns a newly issued installation or rotated token only to the authorized admin call, while the admin page displays it until the page closes. Public staging TLS, a deployed-package review, managed staff identity and an operational token handoff procedure remain open.

The Connect and withdrawal actor gap found in the follow-up review is now closed in V2 source version 2.5.1 / adapter 7. A live canary requires a configured actor and the current extension version. Profile and sent-invitation inspections report `viewerMatched` from the browser's signed-in profile or `Me` menu. The server binds that fact to the installation, inspection payload, target, config, and recent observation before reserving or authorizing an action; it also requires viewer evidence for confirmation and reconciliation. The content primitive checks again before the Connect Send or withdrawal confirmation click. Missing or different actors fail closed with `VIEWER_MISMATCH`. Fixture and Cockroach tests cover the new boundary, but authenticated observations through the running 2.5.1 extension and any live acceptance are still pending. No live LinkedIn action has been attempted.

Installation tokens can now be rotated through the admin API without changing installation or run IDs. The server stores only the replacement token's SHA-256 hash, returns the token once with `no-store`, and emits an audit event without token material. Claim, authorization, and ACK recheck the hash so an installation object authenticated before rotation cannot continue acting afterward. Focused Cockroach and HTTP tests verified old-token rejection, repeated rotation, preserved installation ID, admin-route authentication, and refusal to rotate a revoked installation. Managed admin identity and an operational token handoff procedure remain open before rollout.

Package review of local build `f47af6c83434` found 12 distribution files and extension 2.5.1 / adapter 7. The manifest requests only `alarms`, `storage`, and `tabs`, with exact LinkedIn, local API, and V2 API hosts. A package scan found no `COCKROACH_DATABASE_URL`, `V2_ADMIN_TOKEN`, private-key marker, `eval(`, or `new Function` occurrence; an exact comparison also found no copy of the configured Cockroach URL. This is local-package evidence only. The current Chrome profile has not run this package, and the public staging package and HTTPS service remain unverified.
