## Transactional state-machine shadow run

`node --env-file=<local server env> scripts/shadow-workflow.mjs 2` used two installations and two concurrent V2 shadow runs for a new test operator, selecting real catalog leads read only. At the final run-completion implementation, runs `826a685b-8bb9-4094-adc2-751f1a895ac4` and `9e7f85c8-0cd0-4d70-b6db-93524a8f787d` each claimed and ACKed two `INSPECT_PROFILE` commands through `ControlPlane`, completed all two leads, reached run status `completed`, and emitted one `run_completed` event. Both had zero action commands, intents, and pay entries. V1 assignment count was 63,135 before and after. The four claim/ACK cycles took 38.7 s total (about 0.1 leads/s, 50 MB RSS). A preliminary two-run, five-lead-per-run trial also completed all ten commands in 73.5 s before the final completion-scoping change; that trial is not final-code throughput evidence.

This exercises real catalog selection and durable claim/ACK/terminal-run transactions, including concurrent runs. The simulated browser facts were not read from LinkedIn. Four final-code commands are not a 1k/10k transactional load, and the measured throughput is too low to claim production capacity; the 1k/10k results above remain bulk-write evidence only.

On 2026-09-26, the same script ran with 10 leads per run against the current V2 backend (`8e5bd29`, source unchanged since `f47af6c`). Runs `9c8bd8a9-ead8-407a-8a7e-90150a4a3811` and `01a944ae-61a0-4c09-86de-284d01a1933e` each selected, claimed, and ACKed 10 real-catalog `INSPECT_PROFILE` leads, then reached `completed` with one completion event. The entire end-to-end script, including setup and final checks, took 121.6 s (about 0.16 completed leads/s overall; reported RSS 49 MB). V1 assignment count remained 63,135. This is a bounded state-machine and isolation check, not an isolated claim/ACK capacity or authenticated-browser result. The 1k/10k figures above measure bulk writes only.

Across the two workers, the largest individual claim took 9.4 s and the largest ACK took 8.5 s. Concurrent workers' call times overlap, so their sums must not be added as wall time. This identifies claim/ACK transaction latency as the next profiling target but does not attribute it to a particular SQL statement or establish production capacity. ## Concurrent claim recovery follow-up

On 2026-09-26, the two-installation, five-lead-per-run workload exposed exhausted Cockroach `40001` retries under the original operator-wide `FOR UPDATE` claim scan. A read-only `EXPLAIN` showed that scan locked the pending index span before filtering runs by installation. Narrowing the lock and lengthening whole-transaction retries did not by themselves eliminate uncertainty retries; the intermediate trials left five unfinished V2 shadow runs. Those runs were paused and their three generated test operators disabled. A read-only check then found V1 assignments still at 63,135 and dev config 27.

The final V2 path discovers expired IDs and the next eligible command in single-statement reads, then locks and rechecks only selected rows inside the transaction. Cockroach's `cockroach_restart` savepoint replays a retryable transaction without discarding its observed timestamps. The final-code shadow run selected and completed five leads on each of two concurrent installations (`ec023f4e-769c-402d-9d0d-04d0a5185bca`, `d08c9b39-14fb-4a04-bcd9-1334135beb7d`). It had 10 observations, one completion event per run, zero actions/intents/pay, and unchanged V1 assignment count of 63,135. End-to-end time was 70.1 s: 20.2 s setup, 48.8 s processing (0.20 completed leads/s), and 1.0 s verification. The SQL profile recorded 12 recovery and 12 candidate discovery reads for 12 claim calls in this sample. This establishes one successful bounded concurrent workload and preserves the production capacity gate as open.
