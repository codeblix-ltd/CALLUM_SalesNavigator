# Support diagnostics validation

The V2 admin support view now joins each diagnostic to its run, lead, command, installation, action intent, and any reconciliation command. It shows the trace ID, extension/build/config version, command and lead state, attempt count, failure stage and code, and selected structured browser facts. It does not return contact email, post text, page HTML, screenshots, or tokens in diagnostic rows.

The backend records a diagnostic for failed profile/inspection observations, an action that ends paused or requires reconciliation, an expired action lease, and an inconclusive comment or withdrawal reconciliation. The action intent and reconciliation command states remain visible after the diagnostic was created, so support can see the current recovery position.

A config-related claim rejection occurs before there is a command. The backend now records a `claim_rejected` event with operator, installation, extension/build/config versions and an allowlisted error code. Repeated failures for the same installation, code and config version are deduplicated within an hour. The admin event view exposes these fields without tokens or page content. A focused Cockroach test passed the incompatible-extension case and checked the event appears in the support view once after two failed claims.

Extension source 2.5.2 adds a local buffer of at most eight structured failure receipts. When a backend request fails before a command or its ACK can reach V2, the worker stores only a random report ID, stage, allowlisted code, optional command UUID, and timestamp. After installation authentication succeeds again, it sends the receipts to `/api/browser-failures` before claiming more work and removes each accepted receipt. A server event key makes replay idempotent, and the backend accepts at most 30 new browser-failure events per installation per hour. It rechecks the installation token and command ownership, derives operator/build/config/run/lead fields from server rows, and discards arbitrary payload fields. The admin event view shows the allowlisted stage, code, occurrence time and correlated IDs without returning event details or page content.

`node --test tests/background.test.mjs` passed 11/11 cases, including a pre-command outage surviving a simulated worker restart, a lost action ACK producing one buffered receipt without another primitive, and rejection of one stale receipt without blocking the next. `V2_TEST_DB=1 node --env-file=<local server env> --test tests/browser-failure.integration.test.mjs` passed 1/1 against a local V2 API process and Cockroach: duplicate replay stored one event; a foreign command and wrong token were rejected; a scoped ACK failure carried its own run/lead/config metadata; injected page HTML and token fields were absent from the stored rows.

`V2_TEST_DB=1 node --env-file=<local server env> --test tests/support-diagnostics.integration.test.mjs` passed 1/1 against Cockroach on 2026-09-26. A failed profile observation had the expected IDs, versions, completed command state, paused lead stage, one attempt, and sanitized mismatch facts. An uncertain Connect had an intent in `reconcile_required` and a pending read-only reconciliation command. A separate V2-only contact fixture stored a test email in an observation; its support row exposed only `contact_email_present=true` and did not contain the address. The affected Connect, comment, and withdrawal integrations then passed sequentially 3/3 with no skips.

These are fixture and local API tests, not a staffed support session or authenticated LinkedIn browser failure. A fully offline browser cannot report until it reconnects, and a local-storage failure cannot persist a receipt; the popup still shows its paused state. The buffered receipts have not been verified in a running Chrome profile. Managed staff identity and an approved retention policy remain prerequisites for broader access.
