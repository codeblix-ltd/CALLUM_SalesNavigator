`public.leads` and `public.lead_niches` are queried read only. `run_leads` stores V2 snapshots and does not claim exclusive ownership against V1. Migration `001` uses `CREATE IF NOT EXISTS`; migrations `002` and `003` expand only the `callum_v2.commands` type constraint and are skipped after their ledger records exist. Rollback means disabling the dev feature flag or restoring the prior config and extension; a future schema correction needs a new numbered V2 migration. No public-schema rollback is allowed. `commands.idempotency_key`, action-target uniqueness, event keys and pay intent uniqueness are enforced by DB constraints. Indexes include operator/status command polling and run/event diagnostics.

Migration `004_comment_action` added only `callum_v2.installations.actor_profile_key`, `callum_v2.comment_drafts`, and the `EXECUTE_COMMENT` command type. The migration and repeat invocation both passed against Cockroach. The comment integration passed separately with direct confirmation, uncertain reconciliation, late ACK, and unique pay line; see [COMMENT.md](COMMENT.md). Connection, inspection, remote config and withdrawal integrations also passed sequentially after this migration. No public-schema alteration ran.

Migration `005_global_action_targets` added the V2-only `action_targets` table with a primary key on `(action_type,target_key)`. It backfilled one guard row per distinct historical action target, preserving all existing intent rows, including duplicate synthetic QA histories. A repeat migration invocation succeeded. Connect, comment and withdrawal now claim the guard in the same transaction as the intent and command; a conflict prevents another V2 operator or lead ID from reserving that target. The rule is intentionally permanent, including when an action later becomes `cancelled`, because an uncertain external submission cannot safely be assumed absent. Direct database writes to `action_intents` bypass the service guard; production writes must use the control plane. This does not coordinate with V1 ownership or prove a live browser click.

A read-only index audit on the existing V2 schema found `commands_by_operator_status`, `commands_by_run`, the action-target primary key, unique intent/event/pay indexes, and operator/run event and diagnostic indexes. At the time of the audit, the V2 command table had 11,501 completed, 26 pending, 25 leased, 17 uncertain and 15 cancelled rows. `EXPLAIN` for the expired-command recovery predicate used `commands_by_operator_status` with spans limited to that operator's `leased` and `pending` statuses, then filtered by expiry. This verifies the selected index path on this catalog; it is not a latency or throughput benchmark under production load.

A later concurrency profile found that the original command-selection `FOR UPDATE` plan locked the whole operator pending index span before filtering by installation. A single-operator, no-expired-row `EXPLAIN ANALYZE` reported 2 ms server execution for the recovery query, while five warmed client `SELECT 1` calls from this machine took 295–325 ms each; neither observation alone explains the full claim latency. Two intermediate concurrent shadow trials exhausted `40001` retries. The final claim path discovers IDs outside the write transaction, locks and rechecks only selected rows, and uses Cockroach's `cockroach_restart` savepoint for retryable writes. An injected retry rolled back its first event insert and committed one event; a real concurrent update preserved both increments. The final 10-lead concurrent shadow run completed with one recovery and one candidate discovery read per claim in its SQL profile. This is bounded evidence; larger transactional loads remain unmeasured.
